# AGENTS.md

Instructions for agents and contributors working in this repository.

## What this is

The Webstone companion website: a static leaderboard for twelve benchmark views across four local Tracks, plus an external BrowserArena Track. Browser side: **LexBench Web Fetch** (live websites, 430 cases across seven categories in its published version) and **WebMainBench** (545 frozen HTML pages, five scored dimensions). Search side: **LexBench Web Search** (149 scenario queries, nDCG@5 / Precision@5 / Success@5) and **SimpleQA Verified** (773 factual queries, Hit@5 / MRR@5 / Answer Match@5). Agent side: **LexBench WebArena Replay** (812 tasks from [ServiceNow/webarena-verified](https://github.com/ServiceNow/webarena-verified), success rate plus end-to-end task and per-action latency at mean / P50 / P95). **LexBench Headless Browser** covers a 372-task subset of the historical [Lexbench Headless Browser](https://github.com/lexmount/Lexbench-Headless-Browser) protocol with signed deltas against a baseline row, PSS in MiB and latency in milliseconds. The evaluation harness that produces the results lives in [lexmount/webstone](https://github.com/lexmount/webstone); this repository only publishes the numbers and renders them.

Page titles use natural English (`Web Fetch`, `Web Search`). Internal IDs stay lowercase and hyphenated (`webfetch`, `websearch`, `lexbench-webfetch`). Never derive a page title by joining a code identifier.

## Layout

- External Tracks use a catalog `url` and open in a new tab with an accessible external-link label. They have no local benchmarks or result files. BrowserArena stays independently deployed.
- `benchmarks/catalog.json` — the only source for Track/Benchmark names, official Dataset names, introductions, resource links and evaluation definitions (metric and category metadata plus table presentation).
- `benchmarks/catalog.json` also owns `providerUrls`, keyed by participant ID. Every participant in every result version needs a verified HTTPS GitHub or official product URL here. Keep project links out of result files; the leaderboard links each participant name to its project in a new tab.
- `results/<id>/<id>-vX.Y.Z-report.json` — one Benchmark's published evaluation version and provenance per file, referencing `id`, `definitionId` and its own `version`. No date subdirectories, manual index or format-version field.
- `scripts/prepare-data.mjs` — scans Benchmark directories, validates filenames/references/values/versions, copies the catalog into `web/public/benchmarks/` and reports into `web/public/results/`, and generates `web/public/results/reports.json` as the page's data bundle.
- `web/` — Next.js app (App Router, Turbopack, static export).
- `Dockerfile`, `.dockerignore`, `deploy/nginx.conf` — direct GitHub-to-Rainbond Dockerfile deployment: build from the repository root with Node.js 22, then serve the static export with Nginx on HTTP port 8080. No Gitea or external image registry is required for this path.
- `web/components/dashboard.tsx` — the single-page dashboard: four Tracks, twelve Bench views, version picker, one results table.
- `web/lib/results.ts` — types, version selection/comparison, sorting, best-value calculation, metric formatting, category helpers.
- `web/lib/presentation.ts` — provider colors; Track icons and table layout remain in the website code.
- `web/app/globals.css` — all styling; there is no component library.
- `web/lib/results.test.ts`, `tests/data.test.mjs` — Node test runner suites.
- `web/AGENTS.md` — rules auto-generated by `next dev`; read it before touching Next.js APIs.

## Commands

```sh
npm install
npm run dev        # prepare:data, then next dev on http://127.0.0.1:3000
npm run build      # prepare:data, then static export to web/out
npm test           # node --experimental-strip-types, both suites
npm run prepare:data
```

Serve a build with `python3 -m http.server 5173 --directory web/out`; never `next start`, the export has no server runtime.

## Data rules

- `benchmarks/` owns reusable definitions; `results/` owns published evaluation versions. Never hand-edit `web/public/benchmarks/`, `web/public/results/` or `web/out/`; all are generated and git-ignored.
- Add a version by adding only `results/<id>/<id>-vX.Y.Z-report.json`; never create or maintain an index file. Each report must contain exactly one Benchmark, matching its parent directory and filename.
- New result releases use `vMAJOR.MINOR.PATCH`, independently per Benchmark. MAJOR changes task populations/reference answers/scoring protocols; MINOR changes measurements/methods/configurations under the same protocol and population; PATCH changes wording/evidence/links only. All versions are immutable files. Require `release: {date, kind, previous, summary}` with an actual UTC publication date, kind `protocol` / `results` / `metadata`, latest previous result version (or null initially), and English summary. Use numeric tuple ordering. See `docs/result-versioning.md`.
- Historical vN files remain unchanged and resolve as vN.0.0 in the UI. Their import dates are retained in source provenance. The leaderboard indicates that the publication date was not recorded. Retain old URL access.
- The top-level `id` is `<benchmark-id>-<version>` and globally unique. Filename, parent directory, Benchmark `id` and `version` must all agree.
- `datasetDifference` is a required English sentence or short paragraph. It states how this published version's task population, selection, reference answers or scoring differ from the Dataset linked by the catalog. Mark unverified correspondence as unknown instead of inventing it.
- Results have no `snapshotDate`, `dateKind`, `schemaVersion`, `measuredAt` or `source.versionId` fields. Use the linked report for source details. Keep actual browser/build version information in method names/configurations.
- Directory discovery runs before dev and build. Restart dev or run `npm run prepare:data` and refresh after adding/removing result files. Static hosting requires rebuilding and redeploying; the browser does not enumerate server directories.
- Keep Benchmark names, official Dataset names, introductions, dataset links, metric labels/explanations/units, category criteria, display precision, table order and default ordering out of result files. Keep provider colors and icons in website code. The validator rejects misplaced Benchmark/page fields in results.
- Each result must reference an existing `definitionId` under that Benchmark. If category meaning, metric calculation or pass criteria change, add a new definition ID and retain the old definition. Do not silently reinterpret old results with the latest definition.
- Actual `taskCount`, `categoryTotals`, `metricSamples`, provider versions/configurations, scores, sample counts, execution notes, evidence and provenance belong to the published result. Derive provider count from the rows.
- Web Extract includes **LexBench SWDE**: ten methods on 800 planned/executed pages. Full-page exact match uses 740 eligible pages (60 excluded for incomplete reference coverage); null handling uses 25 empty reference fields across 24 pages. Keep these denominators separate from `taskCount`. Page-hit macro F1 ranks first, on its supplied 0–1 scale.
- Web Extract also includes **LexBench Zyte Product Extraction**: twelve methods on 140 pages, ranked by full-page exact match. The four field F1 metrics retain three decimals. Full-page exact match uses 140 pages; null handling uses 6 empty reference fields across 6 pages. Keep original-reference distributions separate from source-qualified annotations. Actual reference populations belong in result `metricSamples.note`, which must be nonempty English and is appended to the metric tooltip; never put version-specific counts into reusable catalog descriptions.
- Optional provider `counts[metricId]` contains integer `count` and `total`; it must match the published score at the metric's precision and any shared sample count. Use the `count` unit for page counts, never a percentage or task success surrogate.
- Optional provider `pricing` contains per-1,000-call `min` / `max`, `approximate`, and an English billing `description`. Preserve ranges; never rank them as point prices. Unknown totals have null bounds; `softwareCost` records only a known software charge and excludes model usage. Do not invent billing or interpretation links when none are supplied.
- Every number must be traceable to the evaluation report. Do not invent, interpolate or silently correct a value.
- Search output layers L1, L2 and L3 are scored independently. Never add their scores, mix their candidate pools or depict cross-layer differences as incremental gains. Keep quality-scoring questions separate from timing calls and undisclosed citation denominators.
- Each catalog Benchmark requires separate HTTPS `datasetUrl` and `reportUrl` links. `datasetName` must equal the final path segment of `datasetUrl` and reproduce the official Dataset Card name. These are related navigation resources, not proof of the displayed numbers. A result `reportUrl` is null unless a report for that particular result is supplied; when present, the page shows it alongside the shared catalog Track report. Keep provenance in `source` unchanged.
- A value the source does not publish is `null` and renders as `—`. A genuine zero stays `0`.
- Derived pass counts are allowed when every category count is known; record the arithmetic in `passedDerivation` so the tooltip explains where the number came from.
- Result `categoryTotals` keys must match the referenced definition's categories and sum to `taskCount`; each `provider.categoryPassed` must be within that category total. Known category pass counts must sum to the published passed count. `prepare:data` throws otherwise and the build fails.
- When a new result changes published numbers, update the assertions that pin those numbers in `web/lib/results.test.ts` in the same change.

## Rendering rules

- One table per benchmark, with rank and provider first, then the benchmark's data columns. The default ranking metric is the first numeric column after the provider. LexBench Web Fetch places Task success first, then Request success, then its category columns, then timing metrics. `Passed / Total` is always the last column there. The published version separates 17 embedded-media and 3 direct-media cases.
- Each Benchmark opens on its highest version. A version explicitly requested through the URL is shown even when it does not exist, with an English empty state and a `View latest version` action; never silently fall back. A Benchmark with no results also gets an empty state, without an undefined version or a broken latest link.
- URL state uses `?benchmark=<id>&version=vX.Y.Z&metric=<id>`. Ignore and drop legacy `date` parameters. When a version does not contain the currently selected metric, fall back to that version's default metric and direction.
- Show the evaluation scope in the selected language beside the result version. Use `datasetDifference` unless there is separate display copy for a historical result. Keep the Dataset and Evaluation report links visible.
- The default table shows a compact set of quality and resource metrics; More metrics reveals the remaining disclosed numeric columns; omit wholly undisclosed non-ranking columns. Category breakdown shows category counts by default and can collapse them without discarding data. All visible data columns are equal width: the tables use `table-layout: fixed` with a minimum width, so the table scrolls horizontally only when the container is narrower than that minimum. Do not reintroduce auto layout.
- Row heights are fixed: header and rows 46px on desktop; rows 44px below 760px. Numeric cells remain single-line. Method names and configurations wrap when needed so the full name stays visible.
- The first two columns stay sticky while the table scrolls sideways.
- Output size, timings collected under incomparable conditions and quotes with incomparable billing bases use catalog `highlightBest: false`: allow numeric sorting without declaring a winner.
- Highlight the best value in each comparable column independently, using the metric's `direction`. Category pass counts and `Passed / Total` use the highest value. Ties are all highlighted; a column with fewer than two disclosed values or identical values has no winner. `null` and `—` are excluded; real `0` and negative signed deltas participate. Use deep-green bold text on a very light green background and include a screen-reader `Best in this column` label. Do not highlight an entire row.
- Highlight the whole header of the currently sorted column with a light green background, darker bold text, the direction arrow and `aria-sort`. Changing sort direction must not mark the worst value as best.
- English is the first-visit default. Support a complete explicit English/Chinese switch, persist the preference locally and update the document language. The catalog owns translations of reusable definitions; reports own translations of new version-specific text. Historical edits live in `web/lib/result-copy.ts`. Official project, model and Dataset names, navigation group names and Track names retain their English spelling in both languages. Translate descriptions and actions.
- Default result display text remains English. Preserve original source quotations and provenance; supply display translations separately rather than rewriting original evidence.
- The download link must show `Download Report` in English and its Chinese translation in Chinese, including on mobile, and use the same accessible name as its visible label. It downloads the file for the selected version. Do not add a hover tooltip or rely on one to explain the action.
- All local Tracks and Benchmarks share the same table geometry, typography, controls and capability-profile layout. Use the shared metric selector for radar axes; tables use the common More metrics and Category breakdown buttons. Data availability may change the available options; do not introduce Track-specific styling or alternate controls. Keep the ranking column visible. Radar controls offer a reset and require at least three axes to draw a chart.
- Keep the dependency surface small; prefer plain CSS in `globals.css` over new UI packages.

## Security

- No tokens, keys or credentials in code, data, documentation or commits. `.env*` files stay local. Navigation distinguishes the evaluation repository (`lexmount/webstone`), result submissions (`lexmount/webstone-site`) and Datasets. Star links point to `lexmount/webstone`.

## Result submissions

- Internal and external result contributors use the same personal-fork PR flow. A Webstone installation is optional. The homepage offers a copyable submission prompt. Submission links open the agent instructions in the webstone-site README, and legacy `/submit` links redirect there.
- Published report files are immutable once merged. Corrections and rollbacks append a new version and explain the change. Result-only PRs may add participant URLs but cannot change definitions or application code.
- `scripts/check-result-change.mjs` is the trusted base-branch PR boundary. It must inspect candidate Git blobs without running submitted code or receiving deployment credentials. Keep it separate from the ordinary unprivileged website build.
- New submissions require public HTTPS evidence URLs. Local CLI preflight is not evidence verification; reviewers check measurement provenance and methodology before approval.

## Benchmark presentation

- Match Benchmark names to the official Hugging Face Dataset Card. Modified third-party datasets retain the LexBench prefix; untouched mirrors retain the upstream name. LexBench Zyte Product Extraction includes a separate source-qualified annotation layer, so retains its prefix; do not claim existing scores use that layer without report evidence.
- Name the selected Benchmark once in the main content. Avoid repeating titles, primary metrics, counts or generic sorting instructions in large summary blocks. Put protocol, population and provenance detail in Evaluation notes, with important comparability warnings visible.
- Comparison charts must add information beyond ranking: multidimensional profiles, or quality against comparable latency/resource use. Allow readers to select methods; label scales and preserve missing values. Do not invent composite scores or treat unmatched execution conditions as controlled comparisons.

## Website copy

- For every change to reader-facing text, read `.agents/skills/humanizer/SKILL.md` and `.agents/skills/humanizer-chinese/SKILL.md`. Review the English and Chinese together in the rendered page, including labels, accessibility text, empty states, and text drawn from the catalog or a report. Remove repeated explanations. Keep the facts needed to interpret the results.
- Preserve published result files and source quotations. Put editorial changes to old results in the display copy. Keep metric names, units, sample counts and billing basis accurate in both languages.
- Mark the bilingual copy check in the PR after review. The website check requires that attestation for changes to copy-bearing source files. Reviewers check the rendered text against the underlying data.

## Public delivery

- Reports and blog links must open for an anonymous reader, including embedded previews. Run `npm run check:reports` before publishing. CI checks them on PRs, main updates and daily; HTTP 200 alone does not prove access. Never broaden access without the owner’s authorization.
- Cloudflare Pages publishes `web/out` through the tag-triggered `pages-release.yml` workflow. Tags must be on main history. See `docs/deploying-pages.md` for the established release and verification commands. Keep its `_headers` and `_redirects` behavior consistent with the optional Nginx deployment. Verify the public domain, data, downloads, report access and release identity before shutting down a previous host.

- A definition with `rankable: false` is diagnostic: show values and allow inspection, but render no ranks or best-value highlights, including category and passed-count cells.
- Optional `reports/source-notes.json` is repository-only uploader reference information. Do not bundle it, display its restricted links, treat it as public evidence, or check its link accessibility.

## PR titles and merge commits

Use Conventional Commit titles: `type(scope): English summary`, with an optional scope. Allowed types are `fix`, `feat`, `docs`, `refactor`, `test`, `perf`, `build`, `ci` and `chore`. Prefer 72 characters, keep the title within 100, omit a final period, and use `!` for breaking changes. Run `node scripts/check-pr-title.mjs "fix(ui): align cards"` locally. The required PR title check validates new and edited titles before merge; squash merges use the PR title.

- Presentation uses percentages for percent and 0–1 ratio metrics, seconds for durations, and the original units for counts, scores, MiB and percentage-point deltas. Preserve stored units, precision, numerators and denominators in downloadable results. Keep fractions in cell details instead of repeating them beside every percentage. Official pricing links are catalog resources, not evidence that historical quoted prices equal current rates.
