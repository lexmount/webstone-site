# AGENTS.md

Instructions for agents and contributors working in this repository.

## What this is

A static leaderboard for four benchmarks. Browser side: **LexBench WebFetch** (live websites, 430 cases across six categories) and **WebMainBench** (545 frozen HTML pages, five scored dimensions). Search side: **LexBench WebSearch** (149 scenario queries, nDCG@5 / Precision@5 / Success@5) and **SimpleQA Verified** (773 factual queries, Hit@5 / MRR@5 / Answer Match@5). The evaluation harness that produces the results lives in [lexmount/browser-eval](https://github.com/lexmount/browser-eval); this repository only publishes the numbers and renders them.

## Layout

- `results/index.json` — catalog of every published result file.
- `results/<id>/<date>/report.json` — condensed result data per benchmark.
- `scripts/prepare-data.mjs` — validates each result file, then copies the ones declared by the index into `web/public/results/`.
- `web/` — Next.js app (App Router, Turbopack, static export).
- `web/components/dashboard.tsx` — the single-page dashboard: benchmark switch across the four views, date picker, one results table.
- `web/lib/results.ts` — types, sorting, metric formatting, category helpers.
- `web/app/globals.css` — all styling; there is no component library.
- `web/lib/results.test.ts`, `tests/data.test.mjs` — Node test runner suites.
- `web/AGENTS.md` — rules auto-generated by `next dev`; read it before touching Next.js APIs.

## Commands

```sh
npm install
npm run dev        # prepare:data, then next dev on http://127.0.0.1:3000
npm run build      # prepare:data, then static export to web/out
npm test           # node --experimental-strip-types, both suites
npm run prepare:data
```

Serve a build with `python3 -m http.server 5173 --directory web/out`; never `next start`, the export has no server runtime.

## Data rules

- `results/` is the only source of truth. Never hand-edit `web/public/results/` or `web/out/`; both are generated before dev and build and are git-ignored.
- Every number must be traceable to the evaluation report. Do not invent, interpolate or silently correct a value.
- A value the source does not publish is `null` and renders as `—`. A genuine zero stays `0`.
- Derived pass counts are allowed when every category count is known; record the arithmetic in `passedDerivation` so the tooltip explains where the number came from.
- Category metadata (`benchmark.categories`) totals must sum to `taskCount`, and each `provider.categoryPassed` entry must be an integer within its category total. `prepare:data` throws otherwise and the build fails.
- When a new result changes published numbers, update the assertions that pin those numbers in `web/lib/results.test.ts` in the same change.
- Dates: `snapshotDate` is the import date. Imported results keep `measuredAt: null`; never present an import date as a measurement date.

## Rendering rules

- One table per benchmark, with rank and provider first, then the benchmark's data columns. LexBench WebFetch also renders its six category columns, and `通过 / 总数` is always the last column there.
- All data columns are equal width: the tables use `table-layout: fixed` with a minimum width, so the table scrolls horizontally only when the container is narrower than that minimum. Do not reintroduce auto layout.
- Row heights are fixed: header 54px and rows 60px on desktop; 44px and 48px below 760px. Keep cells single-line (`white-space: nowrap`).
- The first two columns stay sticky while the table scrolls sideways.
- Interface copy is Chinese. README and this file are English.
- Keep the dependency surface small; prefer plain CSS in `globals.css` over new UI packages.

## Security

- No tokens, keys or credentials in code, data, documentation or commits. `.env*` files stay local; `web/.env.local` only ever overrides the public GitHub link (`NEXT_PUBLIC_GITHUB_URL`, defaulting to the evaluation harness repository).
